# 架构说明

## 一句话

单进程、单机、标准库：一个 HTTP 服务把「抓取 → 归档 → 播放 → 逐句学习」串起来，状态存在两个地方——文件（节目目录与音频）和 SQLite（学习记录）。

## 进程与线程

`python run.py` 之后，`app/podcast_server.py` 的 `serve(port)` 会：

| 组件 | 职责 |
|---|---|
| `ThreadingHTTPServer`（主线程） | 只监听 `127.0.0.1`，每个请求一个线程 |
| `worker` 线程 | 串行消费手动任务队列：更新目录 / 下载 / 转写 / 翻译 |
| `vocabulary_worker` 线程 | 消费生词释义任务，数据库里 `pending` 的行就是队列 |
| `feeds.scheduler` 线程 | 每 30 秒醒一次，到点就触发一轮订阅巡检 |

三条工作线程互不阻塞：订阅巡检挂了不影响下载，翻译失败不影响播放。手动队列串行是刻意的——转写和翻译会互相争显存。

## 请求的安全边界

每个请求都要过两道检查：

1. `Handler.trusted()` —— `Host` 必须是 `127.0.0.1:<port>` 或 `localhost:<port>`，`Origin` 如果存在也必须在允许列表里。
2. 写操作还要带 `X-Local-Token`，这个 token 每次服务启动随机生成，通过 `/api/library` 发给页面。

响应统一带 `X-Content-Type-Options: nosniff` 和一条严格的 CSP（`default-src 'self'`，不允许内联脚本、不允许外部连接）。所以即使有别的进程在监听本地端口，也调不动这个服务；页面里也没有地方能塞进第三方脚本。

## 数据落在哪

```
data/
├── library/<slug>/            一个节目一个文件夹
│   ├── catalog.json           合并后的目录（会保留已消失的单集）
│   ├── cover.jpg
│   ├── source_audit.json      每次抓取的 HTTP 回执 + 来源哈希
│   ├── feed_snapshots/        RSS 原文快照，按内容哈希命名
│   └── episodes/<id>/
│       ├── asset.json         文件名、字节数、SHA-256、来源 URL、下载回执
│       ├── episode.json       这一期的元数据
│       └── transcripts/       转写与翻译结果
├── index/
│   ├── shows.json             订阅登记表（关注了哪些节目）
│   ├── schema.sql             SQLite 表结构
│   └── feed-state.json        巡检状态与新单集（运行时生成）
├── archive/<slug>/            取消关注后移到这里，不删除
├── cache/                     临时目录、模型缓存、日志
└── ui.sqlite3                 学习记录（WAL 模式）
```

## 为什么目录是「合并」而不是「覆盖」

`podcast_archive.sync()` 不直接替换 `catalog.json`，而是按 `episode_id` 做并集：新的合并进旧的，旧的如果这轮 RSS 里没有了仍然保留，只是不再出现在 `current_feed_ids` 里。

原因很实际：播客会下架单集、会改标题、会换 CDN。如果每次都覆盖，那些单集会从目录里消失，已经下载的音频就成了孤儿。`learning_status` 和 `first_seen_at` 也一样是合并保留的，不会因为一次同步丢掉学习进度。

`episode_id` 取 `guid` 的 SHA-256 前 20 位，没有 `guid` 才退回音频 URL。**不用标题做身份**——发布者随时可能改标题。

## 为什么音频不能断点续传

`download()` 会先写 `audio.part`，全部下完、校验长度和文件签名之后才改名成 `audio_<hash>.mp3`。中途失败就整个重下。

这不是偷懒：播客的动态广告插入（DAI）会让同一个 URL 在不同时间返回不同的字节。拿两个不同版本的首尾拼起来，会得到一个哈希对不上的文件，还查不出原因。宁可重下。

已经归档的文件永远不会被覆盖。如果本地文件的哈希和 `asset.json` 对不上，程序会报错并保留现场让你查，而不是默默替换。

## 任务模型

手动任务在内存里（`JOBS` 列表），重启就没了。这是有意的取舍：

- 任务本身很轻（一次同步、一次下载），重做成本低；
- 已完成的成果（目录、音频、字幕、笔记）全部落盘，重启不丢；
- 内存队列省掉一套持久化调度器，也不需要处理「重启后任务状态不一致」。

**例外是生词释义和翻译**：它们把中间结果写进数据库，中断后重新开始只补缺失的批次。翻译还有一级缓存（`translation_cache` 表），同样的批次不会重复调用模型。

## 新增功能的接入方式

两处新功能都遵守同一条纪律：**不改原有代码路径，只挂新钩子。**

### 订阅巡检

`app/podcast_feeds.py` 自带线程和状态文件，不去碰 `JOBS` 队列，也不改 `enqueue()` / `worker()`。它复用 `archive.sync()`，所以抓取逻辑只有一份。

新单集的判定：把 `current_feed_ids` 和状态文件里的 `known_ids` 求差集。第一次巡检时 `known_ids` 是空的，此时**不报新增**，而是把当前目录直接设为基线——否则一个三千期的节目会瞬间刷出三千条「新」。

### AI 发现

`app/podcast_discover.py` 分三段，每段都能单独失败：

```
candidates()  →  iTunes 检索（免费、无密钥）
     ↓
recommend()   →  有密钥：模型挑选；没密钥：heuristic_score() 本地排序
     ↓
subscribe()   →  写 shows.json + archive.sync() + 存封面
```

`subscribe()` 走的是和手动添加节目完全相同的归档路径，所以校验、快照、审计一个都不少。单档失败只写进返回结果，不影响同批其它节目。

`app/podcast_llm.py` 是唯一的模型出入口：读密钥、发请求、解析 JSON、把 HTTP 错误翻译成中文。它**不跟随重定向**（避免凭据被转发到别的 host），响应有大小上限，`finish_reason` 不是 `stop` 就报错。

### 前端

`web/extras.js` 是一个自执行函数，做三件事：

1. 运行时创建面板、角标和侧栏入口（原有 DOM 只被 append，不被改写）；
2. 运行时注入 `extras.css`（`index.html` 里没有引用它）；
3. 自己拿 token、自己发请求（优先复用 `app.js` 已有的 token）。

所有新按钮都带 `data-extras-*` 前缀，原界面那个事件委托只认它自己那套 `data-view` / `data-tab` / `data-show` 等属性，所以新按钮不会被误触发。订阅成功后调用原界面的 `loadLibrary()`，新关注的节目会正常出现在侧栏、筛选器和列表里。

## 测试策略

`tests/` 里的 55 个测试全部离线：网络调用用 `unittest.mock` 打桩，`archive.LIBRARY` 和 `paths.*` 指向临时目录，SQLite 用内存库或临时文件。

新功能的测试重点放在**容易出现细微错误的地方**，而不是覆盖行数：

- 首次巡检不能刷屏（基线行为）；
- 同一个单集不能报两次；
- 一个源挂了其它源要照常完成；
- 排序里「节目名命中」必须压过「类型命中」，否则宽泛的大节目会挤掉用户真正描述的节目；
- 取消关注之后文件必须还在；
- 密钥写进文件后，明文不能出现在文件里，也不能出现在任何接口响应里。

## 已知边界

- 巡检是轮询，不是 WebSocket 推送；最小间隔 5 分钟。
- 转写需要 NVIDIA GPU 和约 1.6 GB 模型，且不区分说话人。
- 翻译质量取决于你选用的模型；程序做的是一致性校验（行号、数量、对应关系），不是语义审核。
- 服务是单机单用户的，没有多用户隔离，也没有远程访问。
